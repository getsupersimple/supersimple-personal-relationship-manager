# Changelog

All notable changes to this project are recorded here, one entry per released version
(newest first). Entries are generated from the release commit message for each version's
git tag — see `AGENTS.md` for the workflow that keeps this file up to date.

- **1.85.0** (2026-10-28) — feat: the Settings "Delay between page requests" now paces every paginator — LinkedIn pages, Facebook friend pages (replacing a fixed 300 ms) and the Google Contacts list pages — with a default of 1000 ms (was 500) and a minimum of 250 ms. A blank field or a 0 left in storage by the old Settings page means 1000. `collectCursorPages` (lib/pagination-delay.js) is the shared cursor paginator. Tests: unit tests for the paginator and delay rules, timed LinkedIn end-to-end tests for default, 0, tiny and configured values.
- **1.84.7** (2026-10-28) — fix: restored the delay between LinkedIn page requests so accounts are not rate limited or banned. Cause: the Settings page saved `paginationDelayMs: 0` whenever the field was blank (any settings change did it) and the service worker honoured 0. Now a blank field means the default (500 ms) and the delay can never be below 250 ms, even for a 0 already stored (`lib/pagination-delay.js`). The Settings field has min 250 and an explanatory hint. Tests: timed end-to-end sync tests (a stored 0 was red before) and unit tests for the delay rules.
- **1.84.6** (2026-10-28) — fix(linkedin): LinkedIn sync returned "no connections" because LinkedIn changed its connections response — profile links are now relative (`"url":"/in/<slug>/"`) and names/headlines arrive as `profile_name_loading_state` / `profile_headline_loading_state` strings before the link. The parser reads the new format (older format still supported). Found by replaying the extension's requests against the real LinkedIn page; adds `harness/tests/sync.test.mjs`, an end-to-end test of the real service worker in both formats. Not caused by the 1.84.5 cleanup.

- **1.76.0** (2026-07-27) — experiment(webllm): raise Gemma 3 1B's sliding_window_size override from 512 to 2048, to see if it can actually be used in this app. Traced WebLLM's engine source to confirm sliding_window_size is genuinely runtime-configurable (builds the KV cache's max_total_sequence_length at load time) rather than baked into the compiled WASM — the "_cs1k" in the model's filename is prefill_chunk_size, an unrelated batching parameter, confirmed by Gemma 2 2B using the same "_cs1k" WASM while reliably running at context_window_size: 4096 today. So the 512 ceiling that's been crashing Ask AI on any real contact-context prompt was the model's hosted default value, not a hard runtime limit. Picked 2048 rather than 4096 specifically because a sliding window that size would be numerically identical to no windowing at all for any conversation under 4096 tokens, silently reproducing the earlier-rejected fully-unwindowed attempt (see mlc-engine.js's existing comment) rather than testing anything new. The known risk: Gemma 3's local-attention layers were trained with a 512-token window and RoPE frequencies calibrated for that range, so widening it is architecturally the same category of problem that made the unwindowed attempt incoherent, just a smaller (4x vs ~8x+) extrapolation — untested whether real output stays coherent at this size (1.76.0)

- **1.74.7** (2026-07-26) — fix(webllm): two root causes behind the recurring "lives in Turkey" fabrication, found after ruling out history bleed and stale data.
